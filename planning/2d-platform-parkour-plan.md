# 2D 平台跳跃跑酷：原型制作计划

状态：已于 2026-09-29 写入并应用到 GameCreator，2026-09-30 补充并应用 [v0.1 双人开发与交付计划](v0.1-execution-plan.md)。当前七项任务包括一项已验收的视觉音效方案和六个待执行制作工作包；四个功能系统、九项能力、两项原型入口、首关路线与素材基准已明确。v0.1 以 Godot 工程内完整可玩版本为交付，不安排打包。本文保留早期体验研究方向；本版规则、任务日期、接口和交付条件以 v0.1 计划及 GameCreator 实时记录为准。

## 1. 项目目标与定位

- 目标体验：短关卡、快速重试、靠连续移动保持节奏的横版跑酷。玩家通过读懂地形、掌握起跳时机和壁面动作，逐步缩短通关时间。
- 首发假设：PC 键盘操作，手动左右移动，不采用自动奔跑。用一条 45–90 秒的完整关卡验证“移动是否顺手、失败是否公平、重试是否上瘾”。手柄支持在核心体验成立后评估。
- 核心循环：选关/开始 → 观察前方障碍 → 奔跑、跳跃、蹬墙通过 → 触及终点 → 查看用时与死亡次数 → 立即重试。
- 本阶段排除：战斗、敌人 AI、剧情、随机生成、成长系统、联机、商店及多角色。收集物和排行榜暂不进入首轮原型。

## 2. 最小可玩范围

### 玩家能力

1. 左右移动：有加减速与空中修正，释放方向可及时减速。
2. 可变高度跳跃：按住与轻点形成可辨差异；提供短暂离地补跳和提前按键缓冲，具体时长按试玩调参。
3. 贴墙下滑与蹬墙跳：作为原型唯一进阶动作，支持垂直路线和节奏变化。
4. 死亡后快速重开：同一关卡内即时回到起点；原型先不加入中途存档点。

### 关卡与反馈

- 一条灰盒关卡，按“安全教学 → 单项练习 → 两项组合 → 终点冲刺”四段组织；每段有可读的落脚点和风险预告。
- 障碍只用静态坑洞、尖刺和墙面；碰撞与视觉边界一致。
- 开始、死亡、完成和重试状态清楚；显示计时、死亡次数、最佳成绩（可先仅会话内保存）。
- 临时形状、颜色和基础音效即可；优先验证空间辨识和操作反馈。

## 3. 工作顺序与出口条件

| 阶段 | 主要工作 | 交付与通过条件 |
| --- | --- | --- |
| A. 设计基线 | 将项目类型从旧的“动作 RPG”修订为平台跑酷；确定输入、玩家状态、失败规则、关卡草图及表现规格 | GameCreator 正式内容应用且同步；约定主干入口、共享文件归属与接口 |
| B. 手感实验 | 制作人建立可运行入口、玩家移动/跳跃/蹬墙、碰撞和即时重开；主美并行研究角色识别、危险色和动作/音效反馈 | 灰盒测试房内能稳定完成所有动作；记录参数与失败案例 |
| C. 首关原型 | 拼出四段完整关卡，接入开始/死亡/完成/计时流程；主美交付首批临时视觉及音效 | 从启动到结算可连续游玩；失败后迅速回到可操作状态 |
| D. v0.1 检查与修复 | 主美独立检查同一集成工程，制作人修复并复测，统一交付源工程 | 主路径和统计正确、无阻塞问题，运行说明和验证记录齐全；外部至少 3 名玩家的体验研究安排在交付后 |
| E. 垂直切片决策 | 固定已验证的控制与关卡规则，评估是否扩成 3 关、加入手柄及成绩追逐 | 有同一可玩构建的体验证据、稳定入口和明确内容积压，才进入正式开发 |

以上是顺序与验收门槛，不以日历日期代替实测结果。原型预计保持制作人和主美两条计划开发线；需要独立模块交付时再扩编。

## 4. 分工与依赖

正式里程碑：M1 主干与移动测试房，目标 2026-10-02；M2 v0.1 完整首关集成，目标 2026-10-05；M3 v0.1 修复与工程交付，目标 2026-10-07。日期按 2026-09-30 开始、双人持续投入估算，实际接手时记录实际时间；不以日期代替验收。

正式功能系统：玩家运动（水平移动、可变高度跳跃、墙面动作）；关卡判定（危险/坠落、终点）；流程与成绩（快速重试、计时与成绩、开始暂停与界面导航）；视听反馈（危险与状态提示）。能力状态均为待开发。

- 制作人：维护设计基线、任务排期与主干；本人明确领取核心移动、关卡流程和集成任务，提供可运行入口及自测证据。
- 主美兼技术美术：提出视觉方向、素材规格、危险/安全信息层级、动画和音效方案；在明确领取的任务内制作原型所需表现，提交运行或试听证据，由制作人审核整体可玩性。
- 依赖链：已明确接口 → 移动测试房 → 完整关卡与界面；主美按接口并行制作资源 → 两线汇合集成 → 主美独立检查 → 制作人修复与 v0.1 交付。外部试玩用于交付后的下一版决策。
- 当前两名身份已有正式任务和负责人。主美的 [v0.1 工作包](v0.1-art-work-package.md) 已就绪；任务派发不代表外部助手已接手，未实际开始的任务保持待开始。

## 5. 验证方法与风险

- 技术检查：从项目启动进入关卡；检查碰撞、墙跳、死亡、重开和计时；对高帧率与低帧率下的手感、输入缓冲进行对照。自动检查只能证明规则与流程，不代表好玩。
- 真人观察：记录首次理解操作的时间、各段死亡分布、误以为安全的地形、是否主动再次挑战最佳时间。人数少时只作为方向证据，不当作统计结论。
- 核心风险：蹬墙跳可能增加学习成本；过强惯性可能让失败显得不公平；危险物与背景混淆会造成误判；重开过慢会破坏节奏。每轮只调少量参数并记录构建版本。
- 放行底线：首关不存在软锁；所有致命障碍可预判；失败可迅速重试；玩家能看懂完成条件。若蹬墙不提升体验，应简化为纯奔跑与跳跃路线。
